# Architecture

## One application

An npm workspace keeps the browser app, API and shared request/response types together. React provides reusable task forms, lists, detail panels and filters. Vite handles development and builds, TypeScript catches type mismatches, Tailwind CSS supports consistent responsive styling, and React Router lets users navigate between workspaces without a page reload. Start with list view. A board is optional.

A single Node.js process hosts a modular Express REST API and, starting in Phase 7, Socket.IO. Express routes validate requests, authorization policies decide who can act, services apply business rules, and Prisma reads and writes PostgreSQL. PostgreSQL supplies constraints and transactions, while Prisma provides typed queries and tracks database changes through migrations. Use npm scripts, one lockfile, ESLint and Prettier to make local commands repeatable. The Phase 1 scaffold targets Node.js 22.12+ (22.x) or 24.x with npm 10+, React 19, Vite 8, Tailwind CSS 4, Express 5 and Prisma 7. The initial health endpoint reports API availability. Prisma is configured for PostgreSQL and a separate read-only SQL check exercises the connection. Generate the Prisma Client with the PostgreSQL driver adapter when Phase 2 adds database models.

Serve browser assets, API and sockets through one public HTTPS origin, with Vite proxying API and socket requests in development. This keeps browser cookies and origin checks easier to configure. The server starts as one deployment unit with one PostgreSQL database. Add infrastructure only as operational needs justify it.

## Proposed data model

| Entity          | Relationships and invariants                                                                                                                                                                                                                                                                                                          |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User            | Unique normalized email, password hash and user profile. Owns one personal workspace and can join many teams.                                                                                                                                                                                                                         |
| Workspace       | Type PERSONAL or TEAM. A personal workspace has one owner FK and a unique owner constraint. A team derives its owner and roles from its membership rows.                                                                                                                                                                              |
| WorkspaceMember | Unique workspace/user pair with role and membership status. Database constraint allows at most one active owner per team. Team creation inserts the workspace and owner together. Protect the owner from removal or demotion in the initial release. Retain inactive membership records and clear current assignments during removal. |
| Task            | Exactly one workspace and creator. Optional assignee must match a membership in the same workspace for team tasks, with active membership checked in the write transaction. Stores title, description, priority, progress, deadline instant and IANA zone, and creation, update, completion, archive and deletion timestamps.         |
| TaskCheckpoint  | Many per task, each with author, previous and new progress, comment or description and timestamp. Append-only in application behavior.                                                                                                                                                                                                |
| Comment         | Many per task, each with author, body and timestamp. Separate rows allow discussion independently of progress.                                                                                                                                                                                                                        |
| TeamInvitation  | References team, inviter and registered recipient by user ID. Tracks Pending, Accepted, Rejected, Cancelled or Expired, with expiry and resolution timestamps. At most one pending invitation per team and recipient.                                                                                                                 |
| Notification    | Belongs to one recipient. Stores event type, timestamp and read status. Linked resources are reauthorized before displaying details.                                                                                                                                                                                                  |
| ActivityLog     | Belongs to one workspace and records actor, event, timestamp and optional task reference. Use bounded metadata and preserve historical actor attribution.                                                                                                                                                                             |
| Session         | Belongs to one user. Stores a digest of an opaque random token, idle and absolute expiry, and revocation state or equivalent deletion semantics.                                                                                                                                                                                      |

Use foreign keys, unique and check constraints, including 0–100 progress and paired deadline instant and zone fields. Use composite foreign keys for same-workspace relationships where applicable. Review SQL migrations for constraints Prisma cannot express directly. Index memberships by user and workspace, tasks by workspace with deadline and assignment, history by task and timestamp, and invitations, notifications and sessions by their lookup and expiry paths. Review query plans once representative data exists.

Registration and personal workspace creation form one transaction. Team creation and owner membership form one transaction. Progress and its checkpoint commit together using transactional concurrency control with bounded retries. Acceptance and membership changes commit together with activity and relevant notifications. Resolve pending-invitation expiry on access and before creating a replacement. Use an atomic conditional status transition to prevent accept, reject and cancel races. Expired or resolved invitations cannot be reused. Keep task deletion separate from archiving via a deletion timestamp so deleted tasks are excluded from ordinary views and history remains recoverable for retention purposes.

## Authentication and workspace switching

Validate emails and password strength on the server. Hash passwords with Argon2id. Use a PostgreSQL-backed session and an opaque cookie with HttpOnly, SameSite=Lax and Secure in production. Rotate credentials on login, enforce expiry server-side and revoke on logout. Return a generic invalid-login error, rate limit authentication and invitation requests, and omit sensitive fields from API responses. For cookie-authenticated mutations, require a session-bound CSRF token and validate Origin. Protect login and registration with an origin check. Configure HTTPS, security headers, explicit trusted proxy settings, input limits and same-origin access by default. React escapes text, and comments and descriptions are rendered as plain text.

After authentication, the browser fetches its authorized workspace list. Selecting a workspace changes the React Router URL and fetches tasks, counts, filters and relevant member details keyed by that workspace ID. The login cookie stays the same. Clear the previous view while loading, ignore stale fetches and clear cached user data on logout or loss of access. A direct link follows the same server checks.

For a personal workspace, every task, comment or history operation requires the authenticated user to own the workspace. For a team workspace, the server verifies active membership, resolves the requested task in that workspace and checks its action policy. Return a generic missing-resource response for inaccessible workspace data. Use explicit capabilities so further roles can be added. Proposed default is that owners manage team settings, invitations, roles, membership and all tasks. Members can view team tasks and add comments. They can create tasks when the team setting permits it, and update progress, complete or edit allowed fields on assigned tasks. Owners control assignment, archival and deletion. Validate membership and mutations together where a concurrent revocation matters.

Owners invite registered accounts by email. The app resolves the normalized email to a recipient, creates a time-limited invitation, and shows it in the recipient's in-app inbox. Only the bound, signed-in recipient can accept or reject it. Only an authorized owner can cancel it. Email delivery and OAuth are outside the initial proposal.

## Deadlines and real-time events

Collect date, time and IANA timezone and convert to an exact instant stored as PostgreSQL `timestamptz`. Reject nonexistent local times and require a choice of offset for ambiguous daylight-saving times. Compare the instant with the server clock. An incomplete active task is overdue after its deadline, and pending before or at it, including tasks with no deadline. At 100% set completion time. A completed task is late when completion is after the deadline. Lowering progress reopens the task and clears its current completion time while preserving checkpoints and activity. Archive status takes display precedence. Filter within the selected workspace by archive/completion state, priority, assignee, deadline range and title. Schedule a client refresh around the next relevant deadline because overdue status can change without a write.

Socket.IO shares the session and origin checks. A join request requires a current session and active membership, and the server chooses the room name. Send minimal team invalidations after committed changes to tasks, assignments, progress, comments, completion, archives and membership. Recipients refetch authorized REST data. Keep personal task events out of team rooms and use user-specific notification channels. Remove revoked memberships from rooms, disconnect logged-out or expired sessions and reauthorize recipients before targeting sensitive notifications. Rejoin and refetch on reconnect to catch missed events. Multi-instance operation later needs coordinated room membership, revocation and rate limit state.

## Tests and implementation risks

Use Vitest for time, role and invitation state rules, React Testing Library for routing and workspace state, and integration tests against real PostgreSQL for constraints, authentication and authorization. Cover registration, duplicate email, invalid login, logout, personal workspace creation and CRUD, cross-workspace access, team creation, invite acceptance and rejection, member permissions, assignment, checkpoint ordering, timed overdue status and late completion. Test Socket.IO room authorization, removal and synchronization with multiple accounts and browser sessions. Exercise deadline boundaries, DST transitions, concurrent progress or invitation changes and stale workspace responses.

Key failure modes are cross-workspace data leaks, stale socket access after revocation, race conditions, and incorrect timezone conversion. Build those checks into the relevant phases. Review production logs for sensitive data and verify backups with a restore before launch.
